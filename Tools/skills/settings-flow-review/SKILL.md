# Settings Flow Design & Review

Design what a person understands and accomplishes across the settings set before implementing its pages. Use these principles for the first implementation, additions and later reviews. A page can look tidy and pass its tests while the journey still fails. The agent owns anticipating and resolving those failures; do not wait for the user to find the missing flows.

Keep the task focused on the requested settings/setup experience. Apply the same principles to related menus and system handoffs when they participate in the journey. Preserve the product's established design and the user's accepted decisions. This skill does not turn every task into a whole-app redesign or authorize operations outside the user's scope.

## Establish scope and evidence

- For an existing product, read its current release notes and relevant review/decision records when available before judging the implementation. Identify the source revision, prepared build, installed/running build, and relevant helper/service versions when they differ. A source fix does not mean the user has it. A supplied prototype or fixture may be the entire evidence boundary; do not invent missing release history or search beyond the stated scope to fill it.
- Carry forward previous authorization, rejected alternatives, and protected design choices. Record product-specific preferences with the project; do not convert them into universal rules in this skill.
- Distinguish design-only, authorized implementation, review-only and review-and-fix tasks. A new settings request does not require an existing defect report; establish the intended experience and build it within the authorized scope. Report prioritized findings before fixes when requested. Reporting those findings is a checkpoint within an already authorized task, not a reason to ask again before every page or repair.
- Inspect source, product copy, persistence and asynchronous callbacks as well as the rendered interface. Use the relevant UI/browser skill when interacting with an app. Where live operations are restricted, use isolated fixtures or render states with external mutations stubbed. Label source traces, simulated interactions and live observations accurately.
- When the user and agent share a live desktop, make interaction ownership visible before testing. Use the project's session indicator when available, announce the scope, and check for user handoff requests between short action batches. The indicator must survive app switches/restarts without stealing focus, distinguish active/paused/requested-control states, and end when handing back. Do not imply it locks input or cancels an issued command unless that is actually implemented. Source-only work and truly nonpresenting tests need no takeover notice. Do not infer invisibility from isolated storage, injected hardware, a prohibited activation policy, or a test-runner label: native tests can still order windows front and restore floating panels. Audit window/panel presentation in the test harness and enforce the same session check before running it and before visible action batches. Compile separately before starting a short desktop session.

## Design the first implementation

For new settings or a substantial new flow, establish the following before building individual pages. For an existing set, compare its structure against the same decisions before polishing it. Scale the work to scope: adding one ordinary preference should inherit the existing contract without a whole-app redesign.

1. **Task structure.** Map first setup, ordinary use, adjustment, repair and reset where applicable. Give each task one predictable home and trace contextual entry/return. Show proposed navigation and representative journeys together in a compact outline or inexpensive mockup. Justify each extra page and step. This is reviewable work, not a mandatory approval pause.
2. **Interaction contract.** Apply the defaults below up front: saving and validation, navigation and cancellation, prerequisites and durable completion, scoped resets and recovery. Define what is saved, available, pending and confirmed, and what leaving/reopening does. Resolve legitimate exceptions by the operation's semantics.
3. **Shared implementation.** Encode agreed behavior in suitable shared components and state ownership: page routing, preference writes/error presentation, scoped confirmations, prerequisite status and operation lifetime. Reuse the product's framework; do not create a large generic settings engine for a small task. New pages should inherit these behaviors instead of independently inventing save/exit logic.
4. **Complete first flow.** Implement a representative journey through entry, change, success, failure/retry and return before repeating the pattern across pages. Include applicable empty, unavailable and external-change states from the start. Do not postpone keyboard access, clear wording or responsive layout as cosmetic cleanup.
5. **Verify as built.** Use the checks below as acceptance criteria during implementation. Replay the real entry routes and affected sibling flows; a shared component's passing test does not establish every page's behavior. Capture confirmed new lessons in this skill.

## Map and verify the complete journey

For a complete settings implementation or dialog-set review, read [journey-checks.md](references/journey-checks.md). For a narrow task, apply its relevant checks to the affected journey and shared components without expanding into unrelated work.

Inventory every in-scope page, nested dialog, shared alert, popup, result, permission handoff and entry route. Start with planned routes for new work, then reconcile them with actual call sites and runtime pages; searching for Done, Save or Cancel is only a way to locate controls. Include hidden/error/empty states, advanced and maintenance pages, and dialogs reached from both a menu and Settings. In mixed UI frameworks, a native-constructor inventory may miss declarative sheets and popovers; expand each state-selected child into its actual journeys. Distinguish reachable production pages from retained demos or retired fixture routes before claiming full coverage.

Keep one coverage ledger in the task's existing review record or a suitable artifact. Use a compact structure such as:

| Page / entry routes | User task and applicable states | Save and exit behavior | Evidence / finding | Status |
| --- | --- | --- | --- | --- |

For each relevant feature, follow first use, ordinary use, adjustment, repair, add/remove, and learn/relearn. Cover missing prerequisites, loading, ready, editing, running, success, failure, retry, leaving, reopening and external changes where applicable. Do not manufacture irrelevant combinations. Record a short reason for an omitted material state; do not silently call an unexamined page consistent.

When replacing a workflow, trace each retained capability from its old entry point into the new journey, including detection, profile suggestions, overrides and recovery. A bundled library or passing unit test does not prove the new page calls it or saves its result. Record intentional retirements separately; do not restore rejected features or invent migration requirements. Check an ambiguous/unknown case as well as the easy default, and ensure delayed suggestions preserve explicit choices.

At each transition answer in the user's terms:

1. Where am I, and which device, app or scope does this affect?
2. What is saved, what is currently working, and what is still unknown?
3. What will this action do, and when will it take effect?
4. Is another step actually necessary, or am I already finished?
5. What happens if I go Back, close, switch pages, or return later?
6. If it fails or circumstances change, can I recover here without repeating successful work?

If those answers require knowing implementation details or reading the whole page twice, treat that as evidence to investigate.

## Apply a consistent interaction contract

- Appearance previews must read as previews: use a short label and a quiet frame, keep the sample content inert, and render through the production component. When depicting an existing menu, preserve its real section order; shorten the preview without rearranging sections for color variety. Separate palette swatches may show a deliberately selected range. Focus the sample on the scope being edited while retaining enough neighboring content to judge transitions. Show the actual container edge, inset and shadow on a contrasting backdrop; check Light and Dark samples when each matches the host theme as well as when it differs. A preview card may itself select what is being edited when its selection affordance is explicit; do not expose its sample menu items as working controls. If themes can differ, show their previews together and make the editing scope explicit. For batch editing differing configurations, mark mixed values and change only the touched property in each target; selecting a shared editing mode must not synchronize unrelated values. A saved appearance preset should have an obvious scope, preserve the whole intended configuration, and never overwrite another named preset silently. Hiding optional icons or headings must remove their reserved layout space too.
- When offering appearance presets as design alternatives, demonstrate meaningful differences in composition (such as borders, fill, density, typography and icon treatment), not only color substitutions. Name the treatments for their visual intent and keep palettes independently selectable. A collection intentionally limited to color variations should say so. Preserve the user’s approved baseline and compare alternatives in representative light/dark states. Whenever styling options are added, removed or changed, revisit every built-in preset and record whether to keep, revise, add or retire treatments; do not leave presets frozen around an older option set.
- Multi-device setup must explain the role and action on each device, whose configuration will be used, whether initiation is needed on one or both devices, and where confirmation occurs. Give discovered devices human-readable names; keep an internal identifier, address/port and security comparison code distinct and explicitly labeled when shown. Handle missing discovery metadata, incompatible roles, repeated initiation, success, retry and cancellation. Scope asynchronous errors to the affected discovery service, connection or operation; recovery clears only its own error, and a failed redundant route must not make a working connection look broken.
- Independent, reversible preferences normally save immediately. Explain an exception by the actual validation/transaction need, not by the existence of an Apply button. Preserve the user's chosen product convention when one has been agreed.
- Related fields may need one coherent draft and one explicit commit. Child selections update that draft without a chain of Use/Apply/Save steps. Incomplete or invalid replacement work must not damage the working configuration; save failures preserve the draft and offer a clear retry.
- Keep permission status anchored above an instruction disclosure. Missing access opens the relevant instructions and prevents collapsing required recovery; ready access defaults to collapsed instructions with an optional Show/Hide control. Expanding must not relocate the status, replace the page or lose focus/scroll context. A partial grant must keep each capability’s status explicit. Align actual file drag targets and give each OS handoff one clearly labeled action; do not duplicate a link and button for the same action.
- Completed setup becomes a durable ready/saved state on return and reopening. Make Change, Relearn or Recheck optional. Detect known working defaults before requesting manual setup. A permission or layout that is already working should not keep presenting instructions to grant or teach it.
- When a permission is already enabled but runtime access fails, investigate the current executable, launch context and OS attribution before telling the user to grant it again. A test launched from an agent/terminal can inherit a different responsible identity. Replay the normal user entry route and the restart route; never use a permission reset to hide that mismatch. Show the unavailable capability and an actionable recovery beside its control, including the already-enabled case.
- An unavailable capability does not identify its cause. Review signed-app replacement and stale permission entries as well as launch attribution. Give an already-enabled user a next step when relaunch fails, identify the actual running app/helper, and offer its correct drag/copy target wherever the OS supports adding files. Do not add a meaningless file control to system settings without that capability. A helper file existing is not proof that it is the active permission target.
- Keep saved intent, current availability, last observation, last command, and verified outcome distinct. A saved checkbox must survive an automatic session ending; pair it with inactive/unknown status and an explicit resume route when automatic rearming is unsafe. Test clicking the checked-but-inactive choice: it must turn that preference off, not start the operation. Post-interruption notices need evidence captured when the event happened, durable acknowledgement, and a no-notice case when the feature was off. External changes can invalidate an observation without erasing completed setup. Installed is not responding; sent is not confirmed; connected is not proof of the visible picture or successful hardware behavior.
- Define attention policy when designing automatic behavior: a configured timeout or successful fallback should normally stay in activity/history, without an interruption claiming failure. Require evidence that the outcome broke the user's expected behavior; a saved enable flag alone is insufficient. Account for stale status, callback ordering and prior-session records. An unsolicited incident notice should have its own presentation rather than replacing an unrelated Settings page. Use a standalone modal only when acknowledgement is warranted, defer during existing interactions, preserve the current task and link to relevant history or recovery on request.
- A page with shared Back/Close normally needs no extra Done, OK or footer Back for an informational result. Preserve meaningful operational confirmation and OS-owned picker conventions. Escape, window close, the header and footer must not disagree about saving or cancellation.
- Keep independent information such as About in a modeless informational window or a genuinely navigable page. Do not place it in a Settings shell whose visible sidebar becomes disabled merely to display information. Scoped confirmations and active tests can legitimately block competing navigation; passive product information cannot.
- Re-evaluate navigation when the container changes. A stable page reached through a persistent sidebar normally needs no additional Back/Close content-header control. Do not inherit a dialog's Close fallback inside Settings. Preserve checklist context when setup opens a prerequisite: a contextual return such as Back to setup can help, while ordinary sidebar visits should not acquire wizard navigation. Follow that return through failed repair and refresh, not just the first opening. Keep a scoped exit for temporary operations or drafts that the sidebar cannot safely replace. Prefer inline ordinary editing to rebuilding a nested dialog chain inside the new container.
- Distinguish selecting something to edit from activating it. Keep activation explicit and close to its target when useful, such as a compact Play beside a preset and its shortcut; show the active item independently of the editing selection. Do not remove that distinction merely to eliminate an Apply button. Define None/Unassigned/Off by the operation they perform; an incomplete setup placeholder is not an operating choice.
- Dialog tests must prove which layer they exercise: state assignment, target/action dispatch, or real input through the native modal loop. A mocked confirmation response cannot close a dead-button report. Scope completion to the active dialog and test late timers, background refreshes, and closing/reopening during external handoffs.
- When an action appears unresponsive, distinguish an undispatched action from a saved change hidden by a stale view. Verify both persistence and immediate presentation: new items and changed selections must appear without closing/reopening, including child views that observe a different model.
- Name navigation by its destination and disclosure by what appears. “Review settings” is not a user task: people want to change behavior, restore access, or understand a failure. Reserve Review for inspecting concrete proposed changes or consequences before acceptance. Audit the checklist, feature links, ready-state disclosures and error routes together. If the product has a reset center, make every supported reset discoverable there with explicit scope; do not require users to remember which setup or feature page hides it. A repair link should reveal and highlight the relevant controls within that same reset owner, without selecting a destructive action automatically, while preserving a clearly labeled return to the originating setup step. A specific option need not be a separate page. Verify return after cancellation, failure, completion and retry; opening the generic reset index or rebuilding the setup home does not complete that journey. Explicit sidebar navigation or closing the window must end the temporary return context. Preserve scoped confirmation and keep ordinary editing distinct from erasing configuration.
- Back navigates predictably. Refresh the current page without pushing another copy, changing category, losing scroll/focus or hiding newly added fields. Completion and return wording must fit every entry route.
- Leaving a page is not necessarily cancelling its operation. Before an irreversible action, leaving can abandon the proposal. After it starts, show the true running state and preserve the result if the user leaves. If cancellation is supported, show its actual cleanup outcome before claiming it stopped.
- Check availability before presenting an action as usable, while retaining confirmed readiness when unchanged. Prefer background refresh and event invalidation to forcing a disabled first frame on every opening. Unknown can require a brief checking state; unavailable needs an explanation and a useful repair/setup route. Never fake readiness to avoid a delay.
- Routine background reads should retain the last confirmed display and action availability while unchanged. Unknown initial state, device invalidation, expired evidence and real writes are different states. Serialize a click behind an in-flight read when needed; do not disable on every poll or hide a race by merely changing the color. Audit every periodically refreshed control and test a click during a delayed read. Semantic status/color must come from structured state, not substring matches against assembled text or external names.
- When a feature changes the settings inventory, reopen the first-use/status overview and every shared entry page affected by the new item. Check row capacity, model-to-control indexing, overflow, final-row navigation and unchanged refresh behavior. A new page can work while a fixed-size overview crashes or makes another feature unreachable. Prefer data-driven rows where the inventory can grow; a genuinely fixed domain need not become dynamic without cause.
- A feature invoked before its prerequisites are ready should open the actionable setup/recovery page, preserving the user's request and a navigable way out. An informational Close-only error must not disable a visible settings sidebar. Visiting first-run setup is not proof of completing it: surface unfinished prerequisites for chosen features on return, without forcing unrelated optional setup or claiming readiness while checks are pending.
- Trace maintenance introduced by an app update from the next launch through completion. Do not rely on users discovering a new Setup warning for a component they already installed. Explain required maintenance at the relevant handoff, preserve active work and deadlines, honor OS authorization, and leave a direct retry after cancellation/failure without prompting in a loop. Optional uninstalled components remain optional. Audit generic Repair/Resume buttons: derive routine recovery from saved intent and observed readiness, preserving safety stops and bounded retries. Surface specific failed actions only when intervention is needed; a healthy page must not offer an unnecessary update. OS approval links belong in the action that encountered the missing approval, and reset links must not duplicate an already discoverable reset center.
- Provide a reusable Setup & status overview when first use or recovery spans several categories. It should show what needs attention and the relevant next action, be skippable for optional features, and remain useful after permissions or devices change. It must agree with the feature pages and menus. Where a product has a shared Setup area, give each prerequisite and repeated repair stage one authoritative home there. Feature pages should explain the affected capability and link directly to that stage, not embed competing permission/installation instructions. Keep ordinary behavior choices, device arrangements, learning and session recovery with the feature when they are not prerequisite work.

## Design grouping, language and visual hierarchy

Organize around what people want to do and what the setting affects. Keep a feature's ordinary choices, status and direct links to relevant repair discoverable together; reveal protocol/implementation details only when useful. Explain app-owned versus system-wide effects. Do not relocate a carefully tuned menu or redesign established controls merely to satisfy a preferred layout.

Audit whether each page earns its place before polishing its controls. Compare actual control labels/actions across the main menu, overview, detail pages and subpages; do not audit each page in isolation. After removing duplicated operations, reconsider the remaining page hierarchy: device recognition and layout learning may belong on one page with app exceptions below it, while a category containing only history may become a direct History destination. Update recovery links, instruction text and tests against that final hierarchy. A test that insists on a removed duplicate is an obsolete contract, not a reason to restore it. A page that only repeats routine main-menu actions or links to destinations already in a persistent sidebar is a candidate for removal or consolidation. Preserve distinct configuration, diagnostics and recovery; duplication can be justified for discoverability or accessibility, but name the reason and keep one state owner. When a permission page supplies the exact draggable file with an accessible copy-path fallback, remove redundant Finder-reveal actions; keep instructions and the target available through the System Settings handoff. Distinguish editable device labels from hardware/model identity when reviewing recognition, learned settings and reconnect behavior. Keep prerequisite instructions in Setup, with contextual links when a feature is blocked rather than unconditional duplicate access controls. Where setup spans sidebar items, expose observed readiness beside those items using accessible symbols as well as color; optional or unknown must not become a false green check or a failure. Refresh changed status without rebuilding navigation or disturbing focus. Reserve warning symbols/colors for actionable failures; checking, automatic recovery and acknowledgement waits need a neutral progress state, with timeout/failure transitions that cannot spin forever. Size navigation from complete labels plus indentation, status and scrollbar space; test for actual text truncation as well as contained icon bounds.

For utilities with multiple configurable shortcuts, prefer one searchable/scannable Hotkeys home with feature groups, scope (local versus shared), conflict/readiness feedback and existing harmless tests. Feature pages can link there; avoid competing editors. Fixed shortcuts may be listed as references without implying they are editable. Repeated shortcut editors should share the same control component and order while retaining each feature’s validation and save policy. Share content-sized feedback components too: no reserved error-sized blank space when healthy, complete wrapped errors with reachable recovery when needed, and collapse after recovery. Sweep repeated implementations rather than fixing only the example page. Edit names beside the objects they identify when that saves a separate settings page; keep rename separate from selecting or activating an object, preserve validation and concurrent-edit handling, and visually attach any expanded editor to its object.

Evaluate the number of steps needed to understand and choose, not just the consistency of pages or buttons. A tidy category index can still force people to open each child merely to discover its scope. Put imported or detected pending changes beneath the operation that produced them rather than behind a second Review navigation button; retain explicit confirmation for consequential application. Avoid reserving large empty status regions for possible errors: size to current content, grow for actual failure detail and test that recovery controls remain reachable. Put comparable choices and the information needed to choose them together; prefer inline detail or an inline target picker when the user can decide there. Use a separate page when it supports a distinct task, substantial editing, or necessary confirmation—not merely to repeat an explanation. For tools with independently resettable settings, default to one reset center with an initially unchecked checklist. Show each area’s scope, consequences and any target selector inline; confirm the selected changes together. Use a different structure when the reset is indivisible or requires a distinct recovery procedure. Apply this default according to the independence of the settings, not the app’s genre; it does not replace ordinary settings navigation with checkboxes. For batch actions, explain overlaps, excluded scopes, quit/restart effects, partial results and retry behavior; never silently repeat completed destructive operations.

Guide through clear defaults, status and the next useful action rather than a mandatory tutorial. Use concrete action labels and consistent terms for the same concept. Distinguish changing a preference, testing something, installing a component and performing a destructive action. Do not leave developer/tool names in product copy when they do not help the user.

Check density, grouping and emphasis in actual rendered states. A nominal border can be invisible; a shorter label can still be clipped; color alone does not communicate status. Use cheap prototypes or fixture renders for visual experiments, then verify implemented flows in the actual UI framework. Test relevant themes, small windows, scrolling, focus, keyboard access and accessible names/state. Keep navigation stable across refreshes and asynchronous results.

A settings window with variable content should use the space the user gives it. Review resizing as a journey: sensible minimum dimensions, remembered size across page changes/reopening, reflow or expanded controls rather than empty padding, usable scrolling at smaller sizes, and preserved focus, drafts and active confirmations. Clamp restored geometry to the available screen without making ordinary navigation resize the window unexpectedly.

When rows are added, derive the document size from its contents. A control can paint outside an ancestor's bounds while remaining unclickable; verify native hit testing through the ancestor chain, including the last rows and overflow, rather than relying on direct action dispatch. For table/sidebar cells, check label and status-image bounds after the framework sizes the actual cell: a stored image and accessible status can be correct while the icon is entirely offscreen. Position from cell bounds, accounting for indentation, rather than adding autoresize offsets to a table-width coordinate. Also convert the child bounds into every clipping ancestor: a correctly laid-out cell may itself exceed the visible viewport because of source-list insets or scrollbar gutters. Check both overlay and legacy scrollbars with enough rows to scroll. Sweep other pages built with the same layout helper. Windowless hit tests can establish geometry; keep actual event routing and modal acceptance separate.

Put a feature's session enable/start controls beside the objects it operates on. Saved setup or permission readiness must not imply that a session is running. Show session-off state and the action needed on each participating device in the feature's primary flow; explain restart behavior there. Keep optional automation distinguishable from the prerequisites for ordinary use, with concrete device labels and explicit matching steps where physical identity cannot be inferred. Advanced tuning can retain a separate page without owning a second selection or competing start control.

Exercise the transition from fitting content to overflow when expanding inline editors or showing errors. A scrollbar appearing should not unexpectedly narrow fields or move adjacent controls. Use a stable gutter or an inset overlay appropriate to the product, preserve usable scrolling and focus, and check collapse while scrolled down. Do not hide a scrollbar merely to conceal a layout problem. In a native scroller hosting declarative content, measure height at the actual viewport width: ideal-width intrinsic sizing can clip a wrapped heading even at scroll offset zero. Check the first and last child bounds after narrowing, asynchronous content changes and collapse; extra top padding does not repair an undersized document.

Treat status as a state machine, not a string written only on failure. Trace expiry, reconnection, a healthy response with no error, changed configuration, disabled features and later successful evidence. Separate local failures from relayed peer failures so they cannot echo indefinitely. Name the affected object/computer and the exact recovery action beside the result; “reconnect,” “review results” and “retry” are incomplete if users must discover what they refer to. A read-only recheck and an operation retry must be distinct when retrying changes hardware or other external state. Do not re-request consent merely to clear a status. Setup readiness, an active request and guarantees about future OS behavior are different: describe the observation and its limits without making completed setup look broken solely because uninterrupted future operation cannot be guaranteed.

For optional device automation, use a small schematic and a recognizable example when the physical control is unfamiliar. Prefer a short sequence naming what to do here, what to do on the other device/computer, and the visible sign of success. State its prerequisite and keep optional matching separate from ordinary use; mirror keyboard/mouse flows when the underlying feature supports both. Do not present discovery or saved matching as proof that a real hardware switch was detected.

Before adding persistent status chrome, identify the new decision-relevant information it conveys. Do not repeat an Active badge, selected item or successful autosave in another permanent footer/bar. Put exceptional errors, pending work and actionable warnings beside the relevant control when feasible. Reuse an existing status/count line when the new status replaces that information; routine status changes should not expand cards and shift the working surface. A running operation, ambiguous actual state or global failure can justify persistent status; routine reassurance alone does not.

Use direct dropdowns for ordinary choices when the available options already describe the edit. Scope device/path choices to the object being configured; a convenient global device list can make the wrong physical target look valid. Prefer recognizable connection labels (computer and mapped port) over raw identifiers, retaining identity detail for ambiguity and diagnostics. Distinguish a default from an override and preserve the default when the override changes. Put re-detection beside the setting it repairs, show pending/result/failure states, and never apply a stale response over a newer edit. If a row expands into additional fields, visually associate the row and editor with one bounded area, such as a light background difference and a thin readable outline. Keep its identity and collapse control evident; floating fields between unrelated rows are not enough. Match the product's styling rather than adding a decorated box around every static row.

For spatial configuration, use the user's real objects and relationships in the editor. Keep hardware/profile definition, cable assignment and operating presets distinct. Hidden host-local identities may be necessary internally but should appear only in an actionable identification step when ambiguity requires it. Dragging must use a stable coordinate space and scale for the gesture; snap to the nearest valid edge without forcing unrelated axes or silently changing physical proportions. Preview the snap result and the specific edge/center alignments before drop; provide a temporary modifier to bypass snapping. For connector gestures, keep a small drag threshold, defer click menus until release, highlight compatible targets, and cancel on invalid release, Esc, removal or loss of interaction context without changing saved connections. Make the object body selectable/draggable except for the actual control hit areas; passive labels, spacers and scrolling containers must not create dead zones. Visually attach connectors to their objects and give interactive targets hover/focus feedback. When an occupied connector can hold only one cable, dragging should pick up that cable with a reversible preview and one validated commit, preserving the original on cancellation or failure. Keep essential configuration choices visibly discoverable instead of hiding them behind a connector menu; distinguish choosing a preset route from wiring hardware and activating the preset. Highlight the chosen routes and endpoints for the editing context, with a visible context identifier. Distinguish saved membership, editing selection and confirmed runtime use; a single highlight cannot reliably express all three. Reconcile repeated object cards: rename affordances, hover/focus feedback and the selectable body should work consistently across peer objects, while child actions retain their own hit targets. If objects may be omitted, name the operational result (such as Leave unchanged), and verify that downstream execution actually excludes them. Separate a known physical cable from a runtime display identity that may arrive later; pending identity must not silently grant input control. Reversible tests such as Identify should expose a second press to stop, with generation-safe timeouts that cannot stop a restarted test.

Group a toggle with its dependent value on the same row when they form one decision. When resizing, keep checkbox groups and label/control starting positions anchored; give extra width to useful value editors rather than spreading related controls apart. Keep unavailable subordinate controls visible but disabled when that makes their relationship clearer; avoid conditional layout jumps merely to hide a disabled value. Align native picker labels and control starts with adjacent rows instead of relying on framework-default label spacing. Let a toggle label replace redundant value labels when their association is clear. Scope-specific rows should occupy the same conceptual position (for example, title visibility versus spacing); hide irrelevant controls and ensure stale saved values cannot keep applying an effect the user can no longer edit. Express relative geometry such as fade distance in normalized units when it should scale with a preview or surface, including zero, full-range and overlapping-edge cases. Place visibility choices with title/shape choices. Edge decoration must not change the text’s legibility or interaction area, and mixed-theme edits must still affect only the selected properties.

## Iterate within the same task

1. For existing-flow reviews, report concrete findings with priority, affected journey, trigger, expected/actual behavior, evidence and recommended correction. Functional harm, misleading state, lost work and broken recovery take priority over styling. Separate an observed defect from a design preference or untested hypothesis.
2. For authorized implementation or fixes, complete the work and replay the journey from its real entry point through success, leaving and reopening. Exercise failure/retry or interruption when affected. A screenshot of the replacement page is not a replay.
3. Sweep sibling pages and shared components for the same pattern. A duplicate exit in one alert, incorrect ready state in one setup page, or draft loss in one editor is a reason to inspect the rest of the set immediately.
4. Check for the opposite regression: removing redundant acceptance must not erase meaningful confirmation; caching readiness must not hide disconnection; hiding setup instructions must not conceal a later missing permission; autosave must not commit an incomplete destructive edit.
5. Update findings and evidence, then continue until the authorized scope is handled. Do not leave known implementable work as a new suggestion merely because one batch of tests passed. Keep genuinely blocked hardware/OS acceptance explicit and continue independent safe work.

Use meaningful state-transition and behavior tests for material fixes, not tests that just match a button label or mirror the implementation. Run applicable checks once; broaden or repeat when a new change, failure or unresolved risk warrants it. Do not perform a live reset, hardware change, emergency action, installation or publication solely to obtain review evidence without the necessary authorization.

For implementation and repair, completion requires accounted-for pages/routes, replayed affected journeys, known findings resolved or explicitly deferred/blocked with reasons, and a final report distinguishing implemented behavior, simulated verification, installed behavior and remaining acceptance. For design-only work, deliver the proposed structure, interaction contract and representative state journeys, clearly identified as unimplemented. Report build/install and commit/push status when part of the task. Passing a suite or removing every Done label cannot close the overall review by itself.

## Improve this skill as new lessons emerge

The user explicitly wants this skill to auto-update during use. Confirmed lessons from creating or iterating on a design count too; do not wait for a bug or a separate request to update the skill. When a correction or a demonstrated missed pattern changes the review method, update the skill in that same task; do not merely promise to remember it or wait for another skill-edit request. Do not rewrite it after every routine bug fix.

- Capture the failure mechanism and the missing review question. Generalize only as far as the evidence supports. Keep app-specific ownership, layout choices, permissions and release decisions in the project's record.
- Amend the existing rule or relevant section of `journey-checks.md`; replace superseded guidance instead of appending conflicting rules. Add a discriminating case to [evaluation-cases.md](references/evaluation-cases.md) when it would catch a future recurrence. Include the legitimate exception so the lesson does not become an absolute ban on Save, Cancel, wizards or confirmation.
- Sweep the current app for the newly recognized pattern and rerun the affected journey. A skill edit does not fix the product. Keep both statuses clear.
- Edit the actual installed skill source, resolving a symlink if present, and preserve unrelated instructions. Validate structure/references and assess the changed guidance against realistic cases.
