# System-dialog and focus audit — build 60

Scope: repeat the password-prompt investigation across every production administrator call site, file picker, app alert, System Settings/Finder handoff, and explicit activation/window-ordering site. This is a focus/interaction audit; unrelated open dialog-flow findings remain in V1.2-REVIEW.md. Source baseline: build 59 / f8aa6f5. Prepared build 60 is separate from the installed app and the other test Mac.

## Prioritized findings

- **P1, affected-Mac acceptance still open:** the user could not type into the first lid-install administrator prompt, but cancellation/retry worked. Build 59 removed a competing activation request and withdrew Settings. No actual secure OS prompt was reproduced here. Build 60 extends protection against other app UI appearing during the handoff.
- **P2, source-confirmed and addressed:** `SettingsWindow.open()` did not claim busy ownership for either file-picker path. Parent Back/Close and delayed notices could act while the picker owned the modal loop. Both paths now hold picker ownership; parent navigation cannot terminate that loop, and notices wait for completion.
- **P2, source-confirmed and addressed:** standalone `NSAlert.runModal()` bypassed the shared modal flag. The shared alert runner now marks both presentations busy, refuses overlapping synchronous confirmations, and releases ownership on every return. A refused confirmation returns abort, never approval.
- **P2, source-confirmed and addressed:** permission buttons could request an OS grant prompt and immediately open System Settings. App routes now use the existing direct Settings/drag workflow without also requesting an independent access prompt. Ordinary input-choice saves no longer send a delayed helper permission request; helper configuration observation remains active.
- **P2, source-confirmed and addressed:** external-app links left the Settings panel floating, while unrelated notices could activate Perch during the user's work in the destination app. The panel now stays visible at normal level for drag instructions, and notifications/page changes wait until the user returns. Acceptance of an open request is not treated as completion. A failed URL open restores immediately.

These code paths establish interference risks, not the cause of the other Mac's secure password-entry failure.

## Verification and remaining acceptance

Native AppKit fixtures verify picker ownership/Back/Close, refusal of overlapping confirmations, deferred pages/notices, retained drag UI, failed external open, return notification, authorization after an external handoff, and successful/cancelled/retried/nested authorization restoration. OS operations are injected. A shared-wrapper test is not evidence that every OS dialog accepts typing; route-specific evidence is identified above.

On the other Mac, verify first-attempt administrator typing and cancellation/retry. Also verify file-picker keyboard selection and return from System Settings/Finder with the actual input method used there. No credentials, permission prompts, settings writes, live installation, power action, panic or input/monitor hardware changes were used for this audit. The separate shared lid-control flag defect remains open.

Validation: the final production build and all 20 isolated suites passed, including the new picker-entry and external-link action tests. Strict app/helper signatures and archive integrity were checked before packaging completion. One distinct production warning remains (BW-01). No live OS grant, password entry, installation, panic or hardware operation was performed.
