## Prioritized findings

### NM-01 · P2 · Native validation re-enables unavailable sleep controls

`applyLidSleepPresentation()` disables Including with lid closed while Keep awake is off, and disables both sleep controls for unknown state or a change in progress. `validateMenuItem()` returns true for both. AppKit's subsequent menu validation can therefore replace the intended disabled state with an enabled one.

The isolated production menu reproduced:

- Keep awake off: lid control disabled before `menu.update()`, enabled afterward.
- Both sleep states unknown: both controls disabled before validation, enabled and accessibility-enabled afterward.

The activation handlers have additional reads/guards; this result does not demonstrate an unsafe power command. It does demonstrate a control becoming actionable despite the presentation's readiness decision, including a lid action that can simply do nothing while Keep awake is off.

Share the same explicit readiness decision across presentation, native validation and activation. Preserve useful recovery routes for unavailable state. Evidence: `Sources/main.swift:352–363`, `:473–480`; runtime reproduction in the isolated audit. No sleep control was activated.

### NM-02 · P2 · Keyboard state can be stale on first show and while the menu stays open

Menu opening reads native modifier metadata immediately but queues external Fn reading with a 0.4-second debounce. An ordinary read-only check does not set `blocksFunctionKeyChanges`; the external Fn row continues to display the previous mode and remains enabled until the result arrives. The isolated queue-state check showed `working = true`, `blocksChanges = false`, checked/enabled, and “Without Fn” from the previous result.

There is also a source-confirmed update gap while the menu remains open. The periodic refresh redraws cached `nativeKeyboards` and external Fn results; it does not itself reread modifier metadata or external Fn Lock. The caches update on menu opening, keyboard monitor callbacks and certain explicit/device/global-Fn/activation events. A modifier or firmware-mode change without one of those notifications can remain stale. Cached registrations can also temporarily retain an old external keyboard name and layout-dependent row visibility during discovery.

Maintain appropriate evidence for each property, invalidate relevant changes and distinguish pending/unverified mode from a current one. Use supported notifications or bounded background reads where necessary; do not solve this by forcing all keyboard controls disabled on every opening. Built-in F1–F12 uses a fresh synchronous read during normal refresh and does not have this ordinary cached-mode path.

Evidence: `Sources/main.swift:238–246`, `:287`, `:304`; `Sources/KeyboardModeMonitor.swift:16–19`, `:62–80`, `:136–142`; `Sources/KeyboardSettingsUI.swift:5–15`, `:25–41`, `:89–102`. Pending external Fn presentation was reproduced; physical mode changes and their notification behavior were not executed.

### NM-03 · P2 · Helper-backed rows confuse an initial pending read with failure and repaint late

The helper status getter starts an asynchronous request and immediately returns its cache. A cold cache has no separate loading state for consumers, so the menu can say Watcher offline/Repair needed and hide Resume before the first reply establishes the helper's state. Reply handling updates the cache without a UI notification. Panic, Resume, Settings warnings and input readiness wait for another refresh; while the menu is open, the normal refresh interval is two seconds.

The isolated check rendered Watcher offline, published a fresh healthy helper result, and observed unchanged menu text until explicitly refreshing. The refresh then showed three tracked processes and the active shortcut. This verifies the consumer behavior with injected status; the absence of a production reply notification is source-confirmed.

Keep genuine offline/stale detection, but distinguish no reply yet from a completed failed check. Prime background state and notify affected UI consumers when a result arrives. Apply the same review to the lid client's asynchronous status: it also updates internal state without a menu invalidation callback, leaving periodic refresh to display the change.

Evidence: `Sources/HelperStatusIPC.swift:103–135`; `Sources/PanicUI.swift:13–44`, `:61–67`; `Sources/main.swift:141–149`; `Sources/LidGuardClient.swift:85–107`. No helper was restarted or live permission changed.

### NM-04 · P2 · Scrolling readiness uses the wrong dependency and omits active-state failure

The scroll rows require a fresh guardian status merged with input-helper trust. A fresh, trusted, active input helper can therefore still produce “Set up in Settings” when the unrelated guardian is unavailable. Conversely, with a fresh guardian and trusted input helper, an inactive input event tap still presents saved reversal choices as normal checked “Vertical” controls.

Both cases were reproduced:

- Trusted but inactive input helper: checked/enabled Reverse trackpad scroll, normal Vertical hint and toggle action.
- Healthy input helper, no guardian: Set up in Settings and the permission-setup action.

Base input capability on the actual input helper, and distinguish saved intent from currently running input controls. Retain the ability to turn a saved preference off after access is lost. Offer helper repair versus permission setup according to the actual missing prerequisite. Apply the same fix to trackpad and mouse-wheel rows and their native validation.

Evidence: `Sources/main.swift:272–285`, `:477–478`; `Sources/GuardianInstall.swift:9–18`. Tests changed only the isolated configuration and injected status.

### NM-05 · P3 · The lid menu tooltip still requires an open lid

The settled menu tooltip ends with “Set up the authorized helper with the lid open.” The implemented startup policy since build 47 also supports a closed lid on confirmed external power. The tooltip contradicts that correction even though the main settings/detail paths know the newer policy.

Update the tooltip to match the supported condition. Evidence: `Sources/main.swift:363` and current release notes. This is a source-confirmed wording issue; no installation was attempted.

## Evidence and limits

- Source trace covered all 21 rows, their menu-opening path, the two-second open-menu refresh, native validation, relevant caches, notifications and action guards. System metrics were excluded.
- A separate AppKit executable used copied build-52 isolated sources. Its entrypoint bypassed application startup; helper status was injected, keyboard worker execution was replaced with a no-op, System refresh was skipped, AppleScript/helper installation/physical monitor calls retained the isolated runner's blocks, and configuration writes remained in disposable storage.
- No menu action was activated. No real keyboard write, monitor command, permission reset, panic request, helper installation or power-setting mutation was performed. Some ordinary native metadata/status reads still run in the copied presentation code.
- Runtime evidence covers native sleep validation, helper cache-to-presentation behavior, both scrolling dependency cases and the external Fn pending state. Other conclusions are source traces. Real external-device notifications, OS authorization, physical sleep/audio/input behavior and performance still require their own acceptance.
- No product implementation was changed and no new app build was prepared. The findings are open. The preceding 20-suite pass did not cover these reproduced defects; it is not evidence that this broader menu review had already passed.
