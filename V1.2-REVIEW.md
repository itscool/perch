## Reported bugs to fix in 1.2

These reports describe the original 1.1 failures. The implementation checkpoint below distinguishes source fixes from hardware/OS acceptance still required; automated suites do not disprove user reports.

- **P1 — Build 43 lid cleanup fails before connecting to power control; fixed in build 44.** Reported 2026-09-08: “⚠ Sleep: Lid cleanup failed: macOS power control is unavailable.” `IOPMFindPowerManagement` was incorrectly given `mach_task_self_` in both the lid override and sleep-request paths. Apple's documented argument is the default IOKit port; a read-only open/close check on the affected Mac reproduced failure with the old argument and success with the corrected argument. Build 44 shares the corrected connection setup, adds a real connection regression without power mutations, and upgrades an older installed helper before attempting cleanup through it. Earlier injected-hardware suites missed this connection error. All 20 suites passed; the live app and helpers were upgraded, and the normal lid-helper repair successfully removed the stale session and restarted the build 44 privileged service/watchdog disarmed. Actual closed-lid sleep and failure acceptance remain open. [Apple API contract](https://developer.apple.com/documentation/iokit/1557133-iopmfindpowermanagement).

- **Settings guidance must have one consistent interaction.** Any item saying “See Settings,” “Set up in Settings,” or similar must take the user directly to the relevant settings page when clicked. Use this behavior consistently across the app, including Cycle monitor input and every permission/setup/repair hint. While prerequisites are missing, clicking must perform navigation instead of attempting the unavailable operation. Audit every such label and verify mouse and keyboard activation, the correct destination, and Back/Done navigation. Avoid enabled items that do nothing or merely repeat the warning.
- **First lid-sleep authorization dialog still cannot accept typing.** On the first attempt to change Including with lid closed, the administrator password dialog appears but its input cannot be typed into. Previous menu-dismissal changes did not resolve the user's report. Investigate menu tracking, application activation, settings-window level/focus, and authorization presentation; do not assume the cause is established. Acceptance: the first prompt accepts normal user typing, cancellation preserves accurate queried state, and subsequent attempts work too. Cover both the lid control and master Keep awake paths that require authorization. Verify with a user-operated prompt; never capture, inject, or log a password, bypass authorization, or change live sleep settings as an automated test. Mock success/cancellation tests alone cannot close this bug.
- **P1 — Switching from another Perch-enabled computer leaves monitor state stale.** Reported 2026-09-07: when two computers share a monitor and each runs Perch, a switch performed by one computer can leave the other believing its previously selected input is still active. Its next cycle can therefore choose the wrong destination or appear to do nothing. Reproduce with computers A and B: switch through Perch on A, change the monitor input through Perch on B, then inspect A's displayed state and next-switch decision; repeat in the other direction and after a monitor-button change. Perch needs a discoverable way to check which input the monitor is actually displaying, and must reconcile external changes before deciding the next input. Distinguish a fresh monitor report, a user-confirmed observation, and the last command sent; remembering which port belongs to this Mac does not establish the current input. If the monitor or connection cannot report the active input, show it as unknown/unverified and offer an explicit recovery or destination choice rather than implying that a cached value is current. The existing **Read current input** control and pre-cycle reads are implementation starting points, not proof that this two-computer flow works. Acceptance: supported readback detects changes made by either computer or the monitor's buttons; subsequent cycling uses the actual input; failed, unsupported, or stale readback never presents the last command as verified current state; and users can recover without guessing a cycle position. Verify the complete two-computer journey with user-operated hardware checks; do not switch live inputs during the review or close this report using mocks alone.

### Consistent saving and task boundaries

The user challenged the monitor-specific Apply button. The former protocol trial suspended saving for the entire monitor form, despite a label implying only the protocol would be applied; Done could then discard otherwise ordinary edits. Keeping a working setup intact justifies an editable proposal, but not a hidden change to the page’s saving rules.

- Independent ordinary controls save immediately and report their result. Back or closing leaves the page; it must not silently discard ordinary edits.
- Related setup fields that need validation together live in an explicitly separate Save/Cancel editor. Save commits the described setup; Cancel preserves the previous one. Validation/save failures retain the draft and keep the editor open.
- Read, Check, Recheck, and Detect do not commit a proposed replacement. Monitor connection checking is now separate from Use this connection, which returns a checked proposal to the setup draft. The final setup Save commits it. Editing the endpoint after a check invalidates acceptance of that check.
- An action that accepts a learned or tested result names that result, such as Use this layout or Use this input list, and explains when the result is saved. A draft’s feedback must not replace the operating feature’s status.

Implemented for monitor settings with isolated regression coverage of immediate saving, protocol/list/connection drafts, Save, Cancel, failed Save, Undo, stale checks, and return to the ordinary page. Apply this contract in the remaining whole-app grouping/flow pass; this does not claim that every existing page already meets it.

## Multi-monitor and lid-grace implementation checkpoint — 2026-09-08

Both requested features now have source implementations. They have not been installed, enabled on live hardware, or published. This checkpoint supersedes the earlier “pending implementation” notes; those dated checkpoints remain as review history.

- **Display groups:** explicitly include one, either, or several monitors. Give each computer a named destination with an independent port mapping per selected display. A newly discovered display is never added to a group. Duplicate models have stable identity suffixes, editable group labels, and an explicit Identify action. Disconnected members retain their labels and remain in the requested scope.
- **Current input and recovery:** Check current inputs performs fresh reads. Cycling chooses one group destination only when every member freshly reports the same saved destination. Mixed, unreadable, or unmapped inputs open the named-destination recovery path. Writes report each display as confirmed, failed, or unverified. Retry includes only incomplete members, tolerates reconnection, and rejects changed mappings. Neither atomic switching nor rollback is promised.
- **Settings contract:** ordinary group selection/activation saves immediately. The group editor commits a related set of names, members, destinations and shortcut together through Save group. Back/Close discards that draft. Saving, checking, and identifying do not switch monitor inputs. Existing menu rows remain; the existing cycle action uses an explicitly activated group.
- **Lid policy:** powered closed-lid operation has no session limit. Closing on battery or undocking while closed begins 60 seconds to open the lid. Opening cancels it. Reconnecting power cancels enforcement; five seconds of stable external power resets the next undocking interval, while brief power flapping retains the earlier deadline. The clock includes sleep and ignores wall-clock edits. Expiry releases clamshell prevention before requesting system sleep.
- **Supervision:** source adds a narrow authenticated root service and an independently observing watchdog. Menu-app leases, watchdog acknowledgment, known power/lid state, matching running-code identity, and successful control readback are needed before Ready. Late renewals do not restart stopped sessions. Restart begins disarmed and cleans up a recorded owned session. The new path does not write a permanent `pmset disablesleep=1`; a legacy override must be explicitly removed first. Quit stops supervised lid operation; ordinary input/agent/idle-awake helpers retain their existing behavior.

**P1 release gates remain.** The clamshell adapter uses Apple XNU's private `kPMSetClamshellSleepState` interface and its shared powerd reason bit. Runtime rejection/readback failure is surfaced, but simulated tests cannot establish compatibility, absence of interference, or bag-safe behavior on real Macs. Verify the first authorization prompt, complete helper installation/upgrade/cleanup, powered/battery transitions at the deadline, actual sleep/wake, supervisor/watchdog/menu failures, and supported macOS/hardware combinations before making a safety claim. Two-computer/multi-display DDC and inactive-video acceptance also remain open. Distribution, uninstall, performance and accessibility gates continue to apply.

### Lid-closed mode with 60-second undocking grace — source implemented; safety acceptance open

**Implementation decision — 2026-09-08:** proceed with the supervised helper implementation. No feature-specific Apple safety approval is pending. The selected private clamshell call has no Apple entitlement check in the published XNU implementation; compatibility and actual sleep/failure behavior still require our own physical testing. Administrator authorization to install the helper is separate from Apple approval. Signing/notarization concerns distribution and does not certify this feature's sleep behavior.

- [ ] **Optional research: native timed assertion shortcut.** Revisit whether Apple provides a supported, third-party-accessible assertion that prevents closed-lid sleep on battery and expires automatically. The currently identified `AppliesToLimitedPower` and `AppliesOnLidClose` options require Apple-internal entitlements, so do not assume Perch can obtain or use them. We may not need this shortcut if the supervised implementation proves reliable; it is not a prerequisite for the current implementation or local build. A supported replacement could reduce custom cleanup/watchdog work. References: [Apple assertion definitions](https://github.com/apple-oss-distributions/IOKitUser/blob/main/pwr_mgt.subproj/IOPMLibPrivate.h), [XNU clamshell dispatch](https://github.com/apple-oss-distributions/xnu/blob/main/iokit/Kernel/RootDomainUserClient.cpp), and [notarization scope](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).

Purpose: keep the Mac working with its lid closed at a powered desk, then give the user 60 seconds to grab it from the dock and open the lid. If it remains closed on battery when that time expires, it must sleep. The undocking grace period is primarily time to open the Mac; reconnecting power can also cancel the deadline. Powered lid-closed operation has no 60-second session limit.

- When this mode is enabled and the lid closes while external power is present, stay awake while that condition holds.
- Entering the lid-closed, on-battery state starts a 60-second grace period, whether the user closes the lid on battery or unplugs/undocks during powered lid-closed operation. Undocking must allow time to carry and open the Mac. If it remains closed on battery at expiry, actually put the Mac to sleep; merely clearing a UI toggle or an idle-sleep assertion does not satisfy the requirement.
- Opening the lid cancels the pending deadline and restores ordinary lid-open behavior. Reconnecting external power before expiry also cancels the deadline and permits powered lid-closed operation. Closing the lid again starts a new close event. Connecting power after the Mac has already slept must not be treated as an instruction to wake it.
- Do not let repeated status updates or power flapping extend an unpowered deadline indefinitely.
- Define external power from the actual power-source state, not battery percentage or a “charging” label; a full battery may still be externally powered. Unknown power/lid state must not authorize indefinite lid-closed wakefulness.
- Show the policy clearly when enabling it: “Stay awake with the lid closed while connected to power. After undocking, you have 60 seconds to open the lid before the Mac sleeps.” Report states such as “Ready · lid-closed operation requires power,” “On battery · sleeping in 43 seconds unless you open the lid or connect power,” and “Lid closed · running on external power.” Any necessary authorization must be obtained before the user closes the lid. Failure to arm or verify enforcement must not appear as Ready.
- Investigate a fail-safe implementation for sleep enforcement across menu-app exit, helper failure/restart, sleep/wake, stale events, and loss of authorization. The current persistent lid override plus ordinary keep-awake assertion must not be assumed sufficient. Resolve how actual sleep is requested and verified without terminating unrelated processes or silently leaving a no-sleep override behind. Do not advertise this as a safety guarantee until the failure cases are demonstrated.

Acceptance requires deterministic state/deadline tests plus user-operated hardware checks for closing plugged in, closing on battery, undocking while closed then opening within 60 seconds, remaining closed on battery after undocking, opening just before/after expiry, reconnecting power just before/after expiry, repeated lid/power changes, power-state uncertainty, and helper/app failure. Do not change live sleep, power, lid or hardware settings during the review.
